Recreate the Lakebase Support App

A Databricks-first walkthrough from GitHub source to a persistent, verified App. Coding is intentionally summarized; the operational steps and failure modes are explicit.

The finished architecture

Signed-in user → Databricks App (Streamlit) → OAuth-authenticated PostgreSQL connection → Lakebase support schema.

The App can stop or redeploy without deleting ticket data. Databricks supplies connection metadata to the App, while the code requests short-lived database credentials at runtime. No database password belongs in GitHub.

Before you start

  • A Databricks Free Edition workspace.
  • A GitHub repository containing an app entry point, dependency file, and app.yaml.
  • Room under Free Edition limits: one Lakebase project and three Apps.
  • A plan to deploy manually from a public repository's main branch.

Reuse before creating. Free Edition permits only one Lakebase project. If one already exists, use it rather than trying to create another.

Manual Databricks walkthrough

Confirm the GitHub source is deployable

Push the application to a public GitHub repository on main. At minimum, the root needs the app entry point, requirements.txt, and app.yaml. Our repository is cookx775/ai-support-app.

Keep credentials, .env files, cached files, and local virtual environments out of Git.

Create or identify the Lakebase project

Databricks workspace → Lakebase Postgres Autoscaling

Create a project only if the account does not already have one. A new project normally provides a production branch and databricks_postgres database. This build reused the existing project new-database.

Record four names: project, branch, database, and primary compute endpoint. You will select the first three when attaching the resource and use the endpoint resource name in app.yaml.

Copy the endpoint resource name—not its UID

Lakebase project → production branch → Overview → Computes → primary → Get ID → Copy resource name

The working value had this shape:

projects/new-database/branches/production/endpoints/primary
Most important pitfall: the project, branch, and endpoint screens also show UUID-style UIDs. Passing those UIDs to the OAuth credential API caused an “Endpoint not found” error followed by a connection-pool timeout. Use the value labeled resource name.

Place the endpoint resource name in the App configuration

Set a non-secret environment value such as ENDPOINT_NAME in app.yaml. The runtime command should start the web server on 0.0.0.0 and port 8000, which is the port expected by Databricks Apps.

Commit and push the configuration. The endpoint resource name identifies infrastructure but is not a password.

Create the Databricks App

Databricks workspace → Apps → Create app → Custom app

Name it ai-support-app and add a short description. Databricks creates an App service principal; this identity is what the deployed process uses when it connects to other Databricks resources.

Configure Git as the App source

Choose GitHub, enter the public repository, and select main. A public repository does not require a Git credential. Confirm the App overview shows the expected repository and branch.

Automatic GitHub deployment was unavailable for this public-repository setup because the feature requires a private repository and Git credential. Use the App's Deploy button after each push.

Attach Lakebase as an App resource

In the App's resources or configuration flow, add a Database resource. Select:

  • Project: new-database (or your project)
  • Branch: production
  • Database: databricks_postgres
  • Permission: Can connect and create

Databricks then authorizes the App service principal and injects PostgreSQL settings such as PGHOST, PGDATABASE, PGUSER, PGPORT, and PGSSLMODE.

Understand the one coding detail that affects operations

The application should not expect a static PGPASSWORD. It should use the Databricks SDK to generate a short-lived OAuth database credential for the endpoint resource name, and renew credentials when the connection pool opens new connections.

The remaining implementation can vary. This app creates an idempotent support schema, two related tables, indexes, constraints, and sample data on its first successful startup. All user values are sent through parameterized PostgreSQL queries.

Deploy manually and read the deployment events

App overview → Deploy

A successful deployment progresses through source download, App specification loading, dependency installation, build, and start. Confirm the Git commit displayed on the App overview matches the commit you intended to deploy.

If the build succeeds but the UI reports Lakebase is unavailable, open Logs. An endpoint-not-found error usually means step 3 used a UID. A slow first query can simply be Lakebase waking from scale-to-zero.

Verify the required workflows in the deployed UI

Open the App URL and perform the complete acceptance sequence:

  1. Confirm the three seeded tickets and their messages load.
  2. Create a uniquely named verification ticket.
  3. Add a message to that ticket.
  4. Change its status.
  5. Refresh the entire browser page.
  6. Confirm the ticket, message, and new status remain.

Why refresh matters: it proves the state was committed to Lakebase rather than existing only in Streamlit session memory.

Verify the rows directly in Lakebase

Lakebase project → production branch → SQL Editor

Select the primary compute and databricks_postgres database, then query both tables:

SELECT * FROM support.tickets ORDER BY ticket_id;
SELECT * FROM support.ticket_messages ORDER BY ticket_id, created_at;

Confirm at least three tickets, two messages for every seeded ticket, and multiple statuses.

Verify the foreign key explicitly

SELECT conname, pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE conrelid = 'support.ticket_messages'::regclass
  AND contype = 'f';

The result should state that ticket_messages.ticket_id references support.tickets(ticket_id).

Capture evidence and prepare for grading

Capture one screenshot of the deployed UI showing ticket statistics and records, and another of the Lakebase SQL Editor showing both table names and sample rows. Put the App URL, screenshots, source, checklist, and 3–5 sentence reflection in the submission archive.

Free Edition reminder: an App stops after 24 hours. Restart or redeploy it shortly before grading, then open the public App URL once to confirm it is responsive.

What the finished result looked like

Retrieval check

Which Lakebase identifier belongs in the OAuth credential request?

The endpoint resource name, such as projects/new-database/branches/production/endpoints/primary, not the UUID-style project, branch, or endpoint UIDs.

What proves the data is operationally persistent?

Create or update data through the deployed App, perform a full browser refresh, and confirm the state is re-read from Lakebase. A direct SQL query provides additional evidence.

Why is no database password committed?

Databricks injects connection metadata and the application generates rotating, short-lived OAuth database credentials using its service principal.
